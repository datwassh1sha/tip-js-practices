## Эксперимент с очередями выполнения

Эксперимент `npm run example:order` (`examples/event-loop.js`).

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | `A B C D E F` | `A` — первое синхронное выражение. `B` печатается при вызове `async`-функции до первого `await`, то есть тоже синхронно. Таймер и обработчик `Promise` только регистрируются. `C` — конец синхронного кода. Затем выполняются микрозадачи: сначала `then` (зарегистрирован раньше), затем продолжение `await null`. Только после очереди микрозадач наступает очередь задачи таймера `F`. |
| Фактический результат | `A B C D E F` | Прогноз совпал полностью. |

Фактический вывод:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
F: задача таймера
```

Разбор:

- синхронный код — `A`, `B` (начало `async`-функции выполняется до `await`), `C`;
- в очередь микрозадач попадают два продолжения: `then` от `Promise.resolve()` и продолжение после `await null` в `demonstrateAwait`. Первым регистрируется `then` (строка 9 файла), продолжение `await` — позже (строка 19), поэтому `D` раньше `E`;
- таймер с задержкой `0` не выполняется немедленно: `setTimeout` ставит задачу, а среда сначала полностью выполняет текущий синхронный код и все готовые микрозадачи, и только затем берёт следующую задачу. Поэтому `F` последняя.

**Собственный обработчик.** В отдельный файл добавлен ещё один `Promise.resolve().then(...)` и второй таймер, чтобы проверить порядок при трёх микрозадачах:

```js
log("A: синхронный код");

setTimeout(() => { log("G: задача таймера"); }, 0);

Promise.resolve().then(() => { log("D: обработчик Promise (первая микрозадача)"); });

async function demonstrateAwait() {
  log("B: начало async-функции");
  await null;
  log("F: продолжение после await");
}

demonstrateAwait();

Promise.resolve().then(() => { log("E: собственный обработчик Promise (вторая микрозадача)"); });

log("C: конец синхронного кода");
```

Прогноз до запуска: `A B C D F E G` — продолжение `await` регистрируется раньше второго `then`, поэтому `F` должно опередить `E`. Фактический результат прогноз подтвердил:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise (первая микрозадача)
F: продолжение после await
E: собственный обработчик Promise (вторая микрозадача)
G: задача таймера
```

Если удалить один из обработчиков `Promise`, соответствующий символ (в основном примере `D` или `E`) просто исчезнет из вывода, а взаимный порядок остальных меток не изменится: синхронная часть по-прежнему выполняется первой, оставшаяся микрозадача — второй, таймер — последним.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовая учебная инфраструктура: маршруты, фильтры, коды ошибок, CORS и отладочные ответы. Не изменялся. |
| `src/api-client.js` | Транспорт: `buildUrl`, `createApiClient`, `requestJson`, `ApiError`. Не знает о предметной модели задач. |
| `src/task-api.js` | Предметный слой: маршруты задач и категорий, проверка фильтров до запроса, проверка схемы после ответа, параллельная загрузка. |
| `src/variant.js` | Только данные варианта: `variantNumber` и `variantFilters`. Ветвления по номеру варианта нет. |
| `src/main.js` | Контрольный консольный сценарий: создаёт клиент, загружает данные, печатает таблицу и обрабатывает контрольную ошибку 404. |

`fetchFn` передаётся в `createApiClient` аргументом, потому что транспорт должен быть заменяемым. Благодаря этому 26 модульных сценариев проверяют URL, заголовки, статусы, `Content-Type`, тайм-аут и отмену без запуска сети и без изменения рабочего кода; отдельный интеграционный набор подтверждает совместимость того же клиента с настоящим API.

HTTP-ошибка проверяется отдельно от сетевой, потому что `fetch` отклоняет Promise только при отсутствии ответа (нет соединения, неверная схема URL, отмена), а ответ `404` или `503` является нормальным выполнением запроса. Если держать `fetch` и обработку `Response` в одном `catch`, созданная вручную `ApiError` вида `http` попадёт в общий обработчик и получит вид `network`, то есть пользователь увидит неверную причину. Поэтому `await fetchFn(...)` находится в отдельном `try`, а проверка статуса выполняется после него.

JSON после разбора всё равно проверяется по контракту, потому что `JSON.parse` подтверждает только синтаксис. Ответ `{"data":"не массив"}` или задача с `completed: "нет"` синтаксически корректны, но непригодны приложению. Проверка схемы в `task-api.js` гарантирует, что вызывающий код получит задачи и категории ожидаемой формы, а неожиданный ответ превратится в понятную ошибку `invalid-response`.

Правила проверки, реализованные в `src/task-api.js`:

- **Задача:** `id` — положительное безопасное целое; `title` — строка, после `trim` длиной от 1 до 100; `completed` — строго `boolean`; `priority` — `low`, `medium` или `high`; `categoryId` — положительное безопасное целое.
- **Категория:** `id` — положительное безопасное целое; `name` — строка, после `trim` длиной от 1 до 100.
- **Уникальность:** коллекция отклоняется целиком, если встречается повторяющийся `id`.
- **`meta.total`:** должен быть численно равен длине `data`; несовпадение — `invalid-response`.
- **Фильтры:** до запроса разрешены только `completed`, `priority`, `categoryId` и `q`; `completed` принимает только `boolean`, поэтому `false` не превращается в строку внутри предметного кода, а `q` нормализуется через `trim`; пустая строка не передаётся в URL.

## Последовательная и параллельная загрузка

Два независимых запроса `/debug/delay?ms=120`, по три замера каждого сценария:

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 313.8 | 248.8 | 248.7 | Время примерно равно сумме двух задержек: второй запрос начинается только после завершения первого |
| `Promise.all` | 124.7 | 125.9 | 124.6 | Время примерно равно одной задержке: оба запроса уже начаты до общего `await` |

Фактический вывод:

```text
Задержка каждого запроса: 120 мс; замеров: 3.
Замер 1: последовательно 313.8 мс, Promise.all 124.7 мс
Замер 2: последовательно 248.8 мс, Promise.all 125.9 мс
Замер 3: последовательно 248.7 мс, Promise.all 124.6 мс

Среднее последовательно: 270.4 мс
Среднее Promise.all: 125.1 мс
Разница: 145.3 мс (ожидаемо около 120 мс при двух запросах)
```

Причинная связь: при последовательном ожидании второй запрос создаётся лишь после того, как завершился первый, поэтому общее время складывается из двух задержек и накладных расходов. В `loadInitialData` оба Promise создаются до `await Promise.all(...)`, поэтому сетевые операции перекрываются и общее время определяется более медленным из двух запросов. `Promise.all` сам по себе не запускает работу — он ожидает уже созданные Promise, а при отказе одного из них итоговый Promise отклоняется, не отменяя автоматически второй запрос. Искусственные задержки в итоговую реализацию не включены.

## Отладка

Точки останова ставились в `src/api-client.js` перед вызовом `fetchFn`, сразу после получения `Response`, перед `response.json()` и в ветке создания `ApiError`.

Успешный запрос `/tasks?completed=false&priority=high`:

| Момент | Наблюдаемые значения |
|---|---|
| До `fetch` | `url = "http://127.0.0.1:5505/api/tasks?completed=false&priority=high"`, `options.method = "GET"`, `options.headers.Accept = "application/json"`, `options.signal` — экземпляр `AbortSignal` |
| После `Response` | `status = 200`, `ok = true`, `content-type: application/json; charset=utf-8` |
| Перед `response.json()` | Проверка `Content-Type` пройдена; тело ещё не прочитано |
| После разбора | `payload.data.length = 3`, `payload.meta.total = 3`, `meta.filters.completed = false` (логическое значение, не строка) |

Ошибочный запрос `/tasks/999`:

| Момент | Наблюдаемые значения |
|---|---|
| До `fetch` | `url = "http://127.0.0.1:5505/api/tasks/999"` |
| После `Response` | `status = 404`, `ok = false`, `content-type: application/json; charset=utf-8` |
| В обработчике ошибки | Тело разобрано как `{ error: { code, message, details } }`; создан `ApiError` с `kind = "http"`, `status = 404`, `code = "TASK_NOT_FOUND"`, `details = {id: 999}` |
| Итог | Исключение не попало в транспортный `catch`, поэтому вид остался `http`, а не `network` |

Ошибка, исправленная в процессе работы: первая версия `normalizeFilters` трактовала явный `null` как «фильтров нет», из-за чего проверка 19 падала — `getTasks(null)` уходил в сеть вместо немедленного `TypeError`. Исправлено так, что `undefined` (аргумент не передан) означает запрос без фильтров, а `null` отклоняется до запроса.

## Вывод

Клиент и предметный модуль реализованы и проверены: `buildUrl` кодирует параметры и сохраняет `false`/`0`, `requestJson` проверяет `Response`, статус и `Content-Type` до разбора, а `task-api.js` проверяет схему задач и категорий, уникальность `id` и согласованность `meta.total`. Все три готовых набора проходят: API — 18 сценариев, клиент — 26, интеграция — 13; четыре собственные проверки также проходят.

Различие видов отказа принципиально: ожидание Promise — это ещё не значение, поэтому без `await` в переменной остаётся `Promise`; HTTP-ошибка (`http`) означает, что сервер ответил статусом вне 2xx, и сохраняет `status`, `code` и `details`; сетевая ошибка (`network`) означает, что ответа не было вовсе; неверный ответ сервера (`invalid-response`) означает, что ответ получен, но не является обещанным JSON или не соответствует схеме; тайм-аут (`timeout`) наступает по `AbortSignal.timeout()`, а отмена (`aborted`) — по внешнему `AbortController`. Смешение этих случаев, например общий `catch` вокруг `fetch` и разбора, приводит к неверной диагностике, поэтому транспортный этап и обработка `Response` разделены.
